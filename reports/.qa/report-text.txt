ABSTRACT 
OrganSync V2 is an educational organ donation and transplant management application built with 
JavaScript and the Next.js App Router. MySQL is the authoritative transactional store. The 
implemented model contains nineteen relational tables, including donation and patient registration, 
organ inventory, waiting-list entries, candidate matches, clinician-recorded compatibility evidence, 
allocation, reservation, transplantation and follow-up history. Twenty triggers and three transaction-
safe stored procedures support integrity beyond browser validation. 
The application separates repositories, services and guarded API routes. Related business changes, 
audit metadata and outbox events are committed atomically. An asynchronous worker delivers 
committed events to MongoDB Atlas using stable event identifiers, retries and idempotent writes. 
Privacy-conscious business projections supplement event and audit collections without replacing 
MySQL. 
This report documents the actual repository, authentic SQL examples, a verified database-object 
inventory and genuine read-only frontend screenshots collected on 17 November 2026. It also 
identifies differences between the supplied conceptual diagrams and the implemented schema. Existing 
rollback-controlled demonstration results are used only as dated historical evidence. Matching is an 
academic workflow requiring clinician compatibility evidence; the system is not a clinically validated 
allocation service or a production medical platform.

1. INTRODUCTION 
Organ donation management requires a persistent relationship between a donor, an available organ, a 
patient’s waiting-list registration and the clinical evidence used to approve a candidate match. 
OrganSync V2 implements these dependencies as an academic DBMS application. Its principal 
contribution is a traceable transition from inventory and waiting demand to allocation, transplant 
recording and append-only follow-up history. 
1.1 Objectives 
The objectives are to represent the workflow using explicit relational keys; prevent inconsistent 
reservations and duplicate transplantation; require clinician-recorded compatible evidence for 
allocation; retain audit and integration events in the same transaction; and demonstrate database 
enforcement using isolated fictional fixtures. A responsive frontend exposes the implemented 
operations and the associated database evidence. 
1.2 Architecture and scope 
The Next.js App Router renders the interface and handles server-side API routes. Services validate 
workflow rules and coordinate transactions; repositories issue parameterised SQL through 
mysql2/promise. MySQL stores the authoritative state. MongoDB Atlas stores synchronised event, 
audit and minimal business projections. Credentials remain server-side in ignored environment 
configuration.

determine clinical suitability independently.

2. PROBLEM DEFINITION 
Separate registers can leave an organ apparently available after reservation, permit duplicate active 
requests, or record a transplant without approved compatibility evidence. The problem is to maintain 
consistent state across these operations while preserving a history suitable for demonstration and 
review. 
2.1 Functional requirements 
Implemented modules cover donor and patient management, organ inventory, waiting-list registration, 
candidate matching, compatibility testing, allocation and release, transplant recording, follow-up 
history, database demonstrations and synchronisation monitoring. The home page links these functions. 
Dashboard and Reports are labelled planned; they must not be presented as completed standalone 
analytical modules. 
2.2 Integrity requirements 
An organ must belong to a donor and a valid type. A waiting-list entry must identify its patient, 
requested type and centre. A match links an organ to a waiting entry of the same type. An approved 
match must have valid compatible evidence recorded by an active clinician. Reservations must be 
exclusive, transplantation permanent, and compatibility and follow-up history protected from 
retrospective editing. 
Allocation, release and transplantation update several related records. These changes must either all 
commit or all roll back. The application also records audit metadata and a durable outbox event in that 
transaction. A later MongoDB outage must not undo a committed MySQL business operation. 
2.3 Assumptions and limitations 
Only fictional demonstration data is appropriate. A candidate preview uses inventory availability, 
waiting status and organ type; it is not a validated medical ranking model. Blood-group and HLA 
compatibility are clinician-recorded evidence, not a substitute for a clinical decision. Development 
authorisation protects local writes but is not production identity management.

One donor may supply several organs, while each organ has one donor. One patient may have several

4. ER TO RELATIONAL MAPPING 
4.1 Steps of Algorithm for Chosen Problem 
Each strong entity becomes a relation with a surrogate primary key. One-to-many relationships place 
the parent key on the child: donor_id on organ, patient_id on waiting_list and match_id on 
compatibility_test. The organ–waiting relationship becomes the associative relation organ_match, 
retaining its own identity so tests and allocations can refer to a specific candidate decision. 
Organ types are normalised into organ_type rather than repeated descriptive text. Allocation and 
transplantation are separate relations because reservation may be released while transplantation is a 
permanent event. Multi-valued follow-up observations form transplant_follow_up. Unique keys and 
specialised mapping relations represent at-most-one restrictions. Audit and outbox aggregate identifiers 
are polymorphic references, not declared foreign keys. 
4.1.1 Normalisation and dependencies 
Atomic scalar values and separate child relations support first normal form. Single-column primary 
keys avoid partial dependency on a composite key. Centre descriptions and organ-type names are held 
in their own relations rather than repeated as descriptive attributes in every transaction, reducing 
transitive update anomalies. Business facts such as allocation status belong to their allocation identity, 
while test observations belong to a test identity. This is a practical normalisation rationale, not a claim 
that every possible semantic dependency has been formally proved. 
Generated active waiting keys and the reservation/permanent mapping tables deliberately materialise 
integrity conditions. Such controlled redundancy is maintained by database constraints and 
transactional services. Foreign keys use ON DELETE RESTRICT, preserving referenced history 
instead of silently cascading it away.

6. DML STATEMENTS 
DML creates and changes data inside the established model. The example below is copied from the 
existing seed file. It is included as source evidence only; no seed was rerun. Contact details and patient 
narratives are unnecessary to demonstrate insertion, so a catalogue example is used. 
INSERT INTO organ_type (organ_name, is_active) 
VALUES 
('Kidney', TRUE), 
('Liver', TRUE), 
('Heart', TRUE), 
('Lung', TRUE), 
('Pancreas', TRUE); 
 
Runtime repositories use parameter placeholders for values and allowlisted table and column 
identifiers. Services place related writes inside a single transaction. A successful registration creates the 
business row, audit metadata and outbox event together. A validation error or SQL exception rolls all 
of them back. Parameter binding protects values from being interpreted as SQL syntax; it does not 
replace authorisation or domain validation. 
6.1 Transactional workflow 
Allocation locks the relevant records, verifies approved compatible clinician evidence, inserts 
organ_allocation and active_organ_reservation, and changes organ and waiting status. Release removes 
the exact reservation and returns eligible inventory and demand to available states. Transplant 
recording inserts transplant and organ_transplant_record, completes allocation and waiting state, 
removes the active reservation, and records audit and outbox entries. Follow-ups are appended rather 
than overwritten. 
START TRANSACTION; 
INSERT INTO donor ( 
    centre_id, 
    full_name, 
    date_of_birth, 
    blood_group, 
    donor_type, 
    registered_at 
) 
VALUES ( 
    1, 
    'Demo Donor', 
    '1995-06-15', 
    'O+', 
    'LIVING', 
    NOW() 
); 
COMMIT; 
 
The transaction example is authentic repository SQL, not a newly executed journey. Actual application 
procedures have additional integrity and audit requirements described in Chapter 8. No UPDATE, 
DELETE, allocation, transplant or fixture creation was executed during report generation.

SELECT ot.organ_name,COUNT(o.organ_id) AS available_count FROM organ_type ot LEFT JOIN organ o ON  
ot.organ_type_id=o.organ_type_id AND o.organ_status='AVAILABLE' GROUP BY  
ot.organ_type_id,ot.organ_name; 
 
The LEFT JOIN keeps every organ type, including types with no available organs. The availability 
condition is in the join predicate, so the outer join is not reduced to an inner join. COUNT(o.organ_id) 
counts matched inventory rows rather than the preserved catalogue row. Grouping by the type key and

7.2 UPDATE Operation 
UPDATE organ_match 
SET match_status = 'TESTING' 
WHERE match_id IN (1, 2); 
 
This seed statement moves the listed proposed matches to testing. It illustrates selection by primary key 
and a state change. Runtime transitions additionally check workflow state, evidence and authorisation. 
The statement is reproduced without execution; affected-row counts are therefore not asserted. 
7.3 DELETE Operation 
DELETE FROM active_organ_reservation 
WHERE organ_id = ? AND allocation_id = ?; 
 
This parameterised operation is used in the allocation workflow to remove only the reservation 
belonging to the expected allocation. It is not a deletion of the organ or transplant history. The 
surrounding transaction updates the related state and records audit/outbox evidence. Foreign-key 
restrictions and immutable-history triggers reject inappropriate historical deletions. No deletion was 
run for this report.

7.4 Correlated Query 
SELECT organ_id, organ_status 
FROM organ o 
WHERE NOT EXISTS ( 
    SELECT 1 
    FROM organ_match m 
    WHERE m.organ_id = o.organ_id 
); 
 
The inner query refers to the current outer organ identifier. NOT EXISTS selects an organ only when 
no corresponding organ_match row is present. It avoids multiplying output rows when several 
historical matches exist. This is authentic source SQL; no new row-level output is reproduced because 
it is unnecessary for the report and may expose identifiers outside the fictional screenshots. 
7.5 Nested Query 
SELECT patient_id, full_name 
FROM patient 
WHERE patient_id IN ( 
    SELECT patient_id 
    FROM waiting_list 
    WHERE status = 'ACTIVE' 
); 
 
The inner SELECT identifies patient keys with active waiting entries. IN then filters the patient 
relation. This is a non-correlated membership subquery; repeated patient keys in the inner result do not 
duplicate a patient in the outer result. 
7.6 Joins and common table expressions 
WITH organ_demand AS ( 
    SELECT 
        organ_type_id, 
        COUNT(*) AS waiting_count 
    FROM waiting_list 
    WHERE status = 'ACTIVE' 
    GROUP BY organ_type_id 
) 
SELECT 
    ot.organ_name, 
    od.waiting_count 
FROM organ_demand od 
JOIN organ_type ot 
    ON od.organ_type_id = ot.organ_type_id; 
 
The CTE separates aggregation from lookup of the descriptive organ name. The same file also contains 
an availability CTE using COALESCE to display zero availability. Existing joins.sql connects matches 
to registrations, patients, organs and organ types for human-readable workflow views. The SQL uses 
actual keys rather than inferring a relationship from names.

9.2 MySQL and MongoDB integration 
MySQL remains the source of truth. Each committed business transaction writes a sync_outbox event. 
The worker uses FOR UPDATE SKIP LOCKED to claim work safely, persists a stable event identifier 
in sync_events, writes audit metadata into audit_history and confirms persistence before marking the 
event DELIVERED. Failure leaves retryable work; retry delay is bounded. A crash before SQL commit 
makes delivery repeatable, so MongoDB operations must be idempotent. 
Business projections use deterministic identifiers and fenced concurrency with generation/checkpoint 
state in projection_sync_state. Projection handlers reread current MySQL state rather than trusting stale 
event payloads. Tombstones represent source deletions, dependency expansion refreshes allocation and 
transplant relationships, and reconciliation handles database changes that bypass application event 
producers. This is application-managed synchronisation, not MySQL binlog CDC.
